## 1. ภาพรวมความเสี่ยงของโปรเจกต์

โปรเจกต์นี้มีเป้าหมายในการนำข้อมูลจาก **Google Earth Engine** มาวิเคราะห์เปรียบเทียบรายปีและรายเขตของกรุงเทพมหานคร และมีแผนเชื่อมข้อมูล **Traffy Fondue** กับ **Open Data** อื่น ๆ ในอนาคต

เนื่องจากโปรเจกต์เกี่ยวข้องกับข้อมูลหลายแหล่ง ข้อมูลเชิงพื้นที่ ข้อมูลรายเวลา และการแสดงผลบนแผนที่ จึงมีความเสี่ยงสำคัญในด้านต่อไปนี้:

- ความถูกต้องของข้อมูล
- ความสอดคล้องของชื่อเขต
- ความถูกต้องของพิกัด
- ความต่างของช่วงเวลาในข้อมูลแต่ละแหล่ง
- ประสิทธิภาพของแอพเมื่อข้อมูลมีขนาดใหญ่
- การตีความผลวิเคราะห์ผิด
- การออกแบบ UI ที่อาจทำให้ผู้ใช้เข้าใจข้อมูลคลาดเคลื่อน
- ความยากในการดูแลโค้ดเมื่อระบบขยายใหญ่ขึ้น

## 2. ความเสี่ยงด้านข้อมูลจาก Google Earth Engine

### 2.1 Dataset อาจไม่เหมาะกับคำถามวิเคราะห์

ข้อมูลจาก Google Earth Engine มีหลายชุด เช่น Sentinel, Landsat, MODIS หรือ dataset ด้านอุณหภูมิ พื้นที่สีเขียว พื้นที่น้ำ และสิ่งปลูกสร้าง หากเลือก dataset ไม่เหมาะ อาจทำให้ผลวิเคราะห์คลาดเคลื่อน

#### ตัวอย่างปัญหา

- ใช้ข้อมูล resolution ต่ำเกินไปสำหรับวิเคราะห์ระดับเขต
- ใช้ข้อมูลคนละ sensor ในแต่ละปี
- ใช้ช่วงเดือนที่ไม่เหมือนกัน ทำให้เปรียบเทียบรายปีไม่ยุติธรรม
- มีเมฆมากในบางช่วงเวลา ทำให้ค่า index ผิดเพี้ยน
- ใช้ composite method ไม่เหมือนกันในแต่ละปี

#### ข้อควรระวังสำหรับ Agent

> [!warning] Agent ต้องตรวจสอบ
> - Dataset ที่ใช้คืออะไร
> - Resolution เท่าไร
> - ใช้ช่วงเวลาเดียวกันทุกปีหรือไม่
> - มีการ mask cloud หรือไม่
> - วิธีคำนวณ index ใช้สูตรเดียวกันทุกปีหรือไม่
> - มีการบันทึก metadata ของ dataset หรือไม่

#### แนวทางป้องกัน

- ระบุ dataset ให้ชัดเจนใน `Data Source Plan.md`
- บันทึกช่วงเวลาในการประมวลผลทุกครั้ง
- ใช้วิธีคำนวณซ้ำได้
- แยก raw data กับ processed data
- เขียน metadata ประกอบผลลัพธ์ทุกชุด

---

### 2.2 การเปรียบเทียบรายปีอาจผิดถ้าวิธีประมวลผลไม่เหมือนกัน

การเปรียบเทียบข้อมูลรายปีต้องใช้วิธีประมวลผลที่สม่ำเสมอ หากปีหนึ่งใช้ค่าเฉลี่ยทั้งปี แต่อีกปีใช้เฉพาะเดือนใดเดือนหนึ่ง ผลลัพธ์จะเปรียบเทียบกันไม่ได้

#### ตัวอย่างปัญหา

| ปัญหา | ผลกระทบ |
|---|---|
| ใช้ช่วงเดือนต่างกัน | ผลวิเคราะห์รายปีผิด |
| ใช้ cloud mask ต่างกัน | ค่า index ไม่สอดคล้อง |
| ใช้ boundary คนละชุด | ค่าเฉลี่ยรายเขตเปลี่ยน |
| ใช้ scale ต่างกัน | ค่าทางสถิติผิด |
| ใช้ reducer ต่างกัน | ค่า mean/max/min เปรียบเทียบไม่ได้ |

#### กฎสำหรับ Agent

> [!danger] ห้ามทำ
> - ห้ามเปลี่ยนวิธีคำนวณรายปีโดยไม่อัปเดตเอกสาร
> - ห้ามเปรียบเทียบ dataset คนละแหล่งโดยไม่ระบุข้อจำกัด
> - ห้ามเปลี่ยน boundary เขตโดยไม่บันทึก version
> - ห้ามแก้สูตร index โดยไม่อัปเดต Methodology

#### แนวทางที่ควรทำ

- สร้างไฟล์ `Methodology.md`
- ระบุวิธีคำนวณ index ทุกตัว
- ระบุปีและช่วงเดือนที่ใช้
- ระบุ boundary version
- สร้างตาราง compare configuration รายปี

## 3. ความเสี่ยงด้านข้อมูลเขตของกรุงเทพมหานคร

### 3.1 ชื่อเขตไม่ตรงกัน

ข้อมูลแต่ละแหล่งอาจใช้ชื่อเขตไม่เหมือนกัน เช่น ภาษาไทย ภาษาอังกฤษ การเว้นวรรค หรือสะกดต่างกัน ทำให้ join ข้อมูลผิด

#### ตัวอย่างปัญหา

| แหล่งข้อมูล A | แหล่งข้อมูล B | ปัญหา |
|---|---|---|
| บางกอกน้อย | เขตบางกอกน้อย | มีคำว่าเขต |
| พระนคร | เขตพระนคร | prefix ไม่ตรง |
| คลองสามวา | คลองสามวา  | มีช่องว่างท้ายคำ |
| บางรัก | Bang Rak | คนละภาษา |
| ป้อมปราบศัตรูพ่าย | ป้อมปราบฯ | ชื่อย่อ |

#### ผลกระทบ

- ข้อมูลบางเขตหาย
- ค่า summary รายเขตผิด
- แผนที่แสดงข้อมูลไม่ครบ
- Dashboard filter ใช้งานไม่ได้
- Insight ผิดพลาด
